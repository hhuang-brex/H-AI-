# LLM Observability — Debugging "Why Did the Model Respond This Way?"

The practical workflow for capturing, storing, and investigating model reasoning + tool calls + decisions in production. The honest framing as of late 2025 / early 2026: **"read the LLM's reasoning" is a leaky abstraction at every layer.** What you can actually read from frontier APIs, what observability platforms can actually capture, and what OpenTelemetry can actually represent are all narrower than the marketing implies. Day-1 instrumentation should plan for the leaks.

## What you can actually read, by lab

| Lab | What's returned | Critical caveat |
|---|---|---|
| **Anthropic Claude 4 / Fable 5 / Mythos 5** | `thinking` content blocks with `display: "summarized"` (default) — produced by a *separate summarizer model* | **Raw reasoning is sales-gated.** Devs see summaries. With `display: "omitted"`, an opaque `signature` field preserves reasoning across turns. |
| **OpenAI Responses API (o-series, GPT-5)** | `reasoning` items, opt-in summaries (`reasoning.summary = auto/concise/detailed`) | **"We don't expose the raw reasoning tokens emitted by the model"** (verbatim from docs). Stateless callers must `include: ["reasoning.encrypted_content"]` to round-trip; the content is opaque. |
| **DeepSeek deepseek-reasoner** | `reasoning_content` field, **verbatim CoT** | **Outlier** — raw access. But passing it back into the next request returns 400. Strip before re-send. |
| **Google Gemini** | Summary parts via `includeThoughts: true`, distinguished by `part.thought: true` | Raw thoughts not API-accessible. `thoughtSignature` is opaque encrypted blob for continuity. |

So when you tell a developer "read the reasoning trace," what they actually get depends on the lab — and on Anthropic / OpenAI / Gemini, that's a summary or an encrypted blob, not the model's actual chain of thought.

## The hidden-billing pitfall

You pay for **full raw reasoning tokens** even though you only see summaries.

- Anthropic: *"You're charged for the full thinking tokens generated by the original request, not the summary tokens. The billed output token count will not match the count of tokens you see in the response."* Even with `display: "omitted"`: *"You're still charged for the full thinking tokens. Omitting reduces latency, not cost."*
- Gemini: *"pricing is based on the full thought tokens the model needs to generate to create a summary, despite only the summary being output from the API."* Read `usage_metadata.thoughts_token_count`.
- OpenAI: reasoning tokens count against `max_output_tokens` and can produce `status: "incomplete"` with `incomplete_details.reason: "max_output_tokens"` — input + reasoning paid, no visible answer returned. Reserve ≥25k tokens for reasoning + output.

Implication for observability dashboards: don't compute cost from visible-content tokens. Read the lab's usage object directly. Otherwise you'll under-attribute spend by 2–10× depending on reasoning depth.

## Multi-turn reasoning continuity — three patterns, three footguns

Each lab has its own protocol. Get one wrong and you lose reasoning across the agent loop.

| Lab | Protocol | Footgun |
|---|---|---|
| Anthropic | `signature` field on `thinking` blocks; pass thinking blocks back unchanged | Strip `signature` and the reasoning is gone for downstream turns |
| OpenAI Responses | Pass back ALL items between last user msg and your function-call output, OR set `previous_response_id` | Drop a function-call item or a reasoning item → reasoning ordering corrupts |
| DeepSeek | Strip `reasoning_content` from message history; don't echo | Pass it back → 400 error |

For trace correlation, your span attributes need to **preserve these items as opaque payloads** — not as parsed/displayed content. Treat them like cookies: round-trip exactly as received.

## OpenTelemetry GenAI — the real state

The spec is in **Development** status (experimental). Stable attributes on a GenAI span as of late 2025: **`error.type`, `server.address`, `server.port`** — that's it. All `gen_ai.*` attributes are still experimental:

- `gen_ai.system` was renamed to `gen_ai.provider.name` (breaking change)
- v1.37 revamped chat-history attributes
- v1.41 renamed tool-call span attributes
- More breaking changes expected before stable

Two opt-in mechanisms developers should know:

1. **Stability switch.** Instrumentations *should* expose `OTEL_SEMCONV_STABILITY_OPT_IN`. Setting it to `gen_ai_latest_experimental` opts you into the latest experimental conventions; otherwise instrumentations continue emitting v1.36.0-or-prior by default.
2. **Content capture is opt-in.** `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions` are **Opt-In** per spec. Instrumentations *"SHOULD NOT capture them by default."* Day-1 advice if you flip them on: store content externally, record only references in the span — otherwise you'll overwhelm your trace backend and/or leak PII.

If you're deciding between OTel and a vendor SDK today: OTel buys you portability across observability backends but the conventions will drift under you. Vendor SDKs are stable but lock you in.

## Observability platforms — what they actually capture

| Platform | Reasoning content capture | OTel GenAI | Notes |
|---|---|---|---|
| **LangSmith** | Token count only via OTel path (`gen_ai.usage.details.reasoning_tokens`); native SDK path may capture more | Yes, named attribute table documented | Reasoning-content capture not documented on the OTel page |
| **Datadog LLM Observability** | Claims native auto-instrumentation for OpenAI / LangChain / Bedrock / Anthropic; specific reasoning-content attribute support not enumerated | "Natively supports OTel GenAI" — but linked from a blog, not the docs index | Treat the OTel claim as **marketing-adjacent until verified against current attribute inventory** |
| **W&B Weave** | Auto-traces Anthropic SDK via `Messages.create()` monkey-patch on `weave.init()`; captures tool definitions + tool-use + tool results | Not the headline integration | Docs don't specifically describe `thinking` block capture |
| **Arize Phoenix** | LLM-traces docs list latency, tokens, exceptions, retrieved docs, prompts, tool calls — **not** reasoning/thinking content explicitly | Via OpenInference/OTel | Absence of doc ≠ absence of capability; verify against your specific instrumentation chain |
| **Langfuse** | Open-source; OTel-native | Yes | Self-hostable for ZDR/PII concerns |
| **Helicone** | Proxy-based capture | Partial | Lowest integration friction (no SDK changes); captures whatever the API returns |

The honest summary: **most platforms capture what the API returns**. They don't synthesize raw reasoning the API didn't expose. Their headline differences are in agent-trajectory replay, dataset promotion from prod traces, and search/UX over the captured data.

## Trace correlation across multi-step agent loops

Independent of platform choice, the table-stakes pattern is one `request_id` (or `decision_id`) propagated across:

1. The user's inbound message (from your app's existing trace)
2. Every LLM call (system prompt + user + tool catalog → reasoning → output)
3. Every tool invocation (input → tool execution → result)
4. Every reasoning item / thinking block / signature
5. The final user-facing output

**Frontier-lab specifics:**

- OpenAI: use `previous_response_id` to chain Responses API calls; the lab persists reasoning across the chain so your trace doesn't have to round-trip it manually.
- Anthropic: pass thinking blocks back across turns (with their `signature`s) — your trace should record these as opaque payloads, not parsed content.
- DeepSeek: strip `reasoning_content` from history; record it in your trace as a side-channel that's never re-played.

If you don't propagate one ID, "why did the model do X" becomes archaeology across systems — see [agent-eval-improvement-tiers](../projects/agent-eval-improvement-tiers.md) for the same concern in the eval lane.

## Replay-with-newer-model — caveats not in the marketing

The pattern: take a historical decision's input fingerprint, run it against a current model, diff the output. Sounds clean. The real-world caveats:

- **Anthropic encrypted `signature` and OpenAI encrypted reasoning** are tied to the *original* model + request. You can't replay reasoning continuity the same way; you replay the inputs and let the new model produce new reasoning.
- **DeepSeek `reasoning_content`** is verbatim but unreplayable in-context (400 on echo). Replays are clean per-call but can't reconstruct prior reasoning state.
- **Summarized-only labs (Anthropic 4, OpenAI, Gemini)**: you're comparing *summaries*, not actual reasoning. Two summaries can match while underlying CoT diverges.

So replay-with-newer-model gives you a clean *output* diff and a clean *cost* diff, but a noisy *reasoning* diff. Plan accordingly. See [prod-shadow-replay](prod-shadow-replay.md) and [decision-audit-trail](decision-audit-trail.md) for the substrate.

## Faithfulness limits

What the labs themselves implicitly concede:

- Anthropic: summaries are produced by *a separate model* — not the target one. The summary cannot be claimed to faithfully represent the target's actual computation.
- OpenAI: explicitly *"we don't expose the raw reasoning tokens"* — and elsewhere notes that hiding raw CoT prevents training pressure on it. The visible artifact is a derived summary.
- DeepSeek: returns verbatim CoT, but no formal claim about whether the verbatim trace faithfully represents internal computation.

Practical implication: the reasoning trace is the **best signal you have for production debugging**, but it's not ground truth for what the model "actually did." For deeper interpretability questions, mechanistic interpretability is its own field — out of scope for production debug workflows.

## Day-1 instrumentation plan

A minimum-viable setup that survives both the API leakiness and OTel drift:

1. **Per-call audit row** with: `decision_id`, `input_fingerprint` (hash of canonical input), `model_version`, full prompt rendered, *whatever the lab returns as reasoning* (summary / opaque blob / verbatim — store as-is in a dedicated column), tool calls, output, lab-reported token usage (read from the lab's own usage object, not from visible-content count), latency, status (`complete` vs `incomplete:max_output_tokens`).
2. **Multi-turn continuity payload** (Anthropic `signature`, OpenAI `previous_response_id` or item list, DeepSeek `reasoning_content` stripped before re-send) preserved as opaque per-turn columns — never displayed, only round-tripped.
3. **One trace ID** propagated from user inbound through all LLM calls, tool calls, and audit rows.
4. **Token-budget assertions** based on lab usage object, not visible tokens. Catches the hidden-billing drift.
5. **External content store** if using OTel content capture; references on spans, content in object storage. Per-spec.
6. **Vendor lock-in posture decision** day 1: OTel GenAI for portability + drift, or vendor SDK (LangSmith / Datadog / Weave) for stability + lock-in. Don't try to do both partially.

## Anti-patterns

- **Counting visible tokens for cost dashboards.** You'll under-attribute by 2–10×. Read `usage` from the lab response.
- **Stripping continuity payloads from logs to save space.** Then replay can't reconstruct the prior turn's reasoning.
- **Echoing DeepSeek `reasoning_content` into the next request.** Hard 400.
- **Trusting `gen_ai.*` attribute names.** They're experimental. Pin a version; expect breaking changes.
- **Inline OTel content capture across an agent fleet.** Backend gets overwhelmed; PII leaks into traces. Use external store + reference.
- **Treating summarized reasoning as ground truth for "why."** It's a derived artifact from a *different* model on Anthropic. Useful, not authoritative.
- **Conflating "captured by the platform" with "queryable / searchable / alertable."** Capture is necessary, not sufficient.

## Eval

- **Cost reconciliation.** Sum lab-reported usage across decisions; compare to your invoice. Drift means an instrumentation gap.
- **Continuity-payload preservation.** Test that round-trip multi-turn reasoning produces identical model behavior under replay. Catches stripped signatures / dropped function-call items.
- **Trace completeness.** Sample N decisions; assert every one has full audit row + propagated trace-id + reasoning column populated.
- **OTel attribute drift.** Pin spec version; alert on attribute renames during dependency updates.
